## 2. 总体设计

### 2.1 技术选型

V1.0 采用**纯浏览器端实现**：HTML + CSS + 原生 JavaScript，数据持久化使用浏览器 localStorage。

- 选择理由：实验环境与演示环境不保证具备服务器/数据库条件；纯前端方案零安装、双击即运行，便于评审和验证；业务规模（活动、报名数据量小）下 localStorage 足以支撑。
- 已知限制与后续方向：数据不跨浏览器/电脑共享，无真实服务端鉴权。后续迭代可将数据访问层替换为后端 API + 数据库，视图与业务逻辑层基本不需要重写。

### 2.2 结构分层

系统在浏览器端按职责分为三层（对应教材"轻量设计：结构、数据、接口、流程"）：

```
┌───────────────────────────────────────────────┐
│              视图层（app.js + index.html）       │
│   登录/注册、活动大厅、我的报名、发布活动、       │
│   我的活动、活动详情/报名名单弹窗、消息提示       │
├───────────────────────────────────────────────┤
│            业务逻辑层（auth.js / app.js）        │
│   注册登录校验、报名规则判断、活动状态计算、      │
│   权限检查、表单校验                            │
├───────────────────────────────────────────────┤
│              数据访问层（storage.js）            │
│   users / activities / registrations / session  │
│   的读写，localStorage 持久化                    │
└───────────────────────────────────────────────┘
```

- 数据访问层统一封装 localStorage 读写，业务逻辑层不直接接触 localStorage，便于后续替换为服务端接口。
- 页面为单 HTML 文件，通过 JS 切换视图（未登录视图 / 学生视图 / 教师视图）。

## 3. 核心业务流程

### 3.1 学生报名流程（核心链）

```
学生登录 → 进入活动大厅 → 浏览活动列表
   → 查看活动详情
       → 系统判断：活动是否报名中？（手动关闭？超过截止时间？）
            否 → 提示不可报名原因
            是 → 填写学号、手机号并提交
                → 系统校验：必填？手机号格式？
                     不通过 → 提示补全
                     通过 → 判断：是否已报名？名额是否已满？
                          不通过 → 提示对应原因
                          通过 → 生成报名记录，人数+1，提示报名成功
   → 在"我的报名"中可查看；报名截止前可取消（名额释放）
```

### 3.2 教师发布与管理流程

```
教师登录 → 发布活动
   → 填写活动信息 → 系统校验（必填、名额正整数、时间先后、截止时间）
        不通过 → 提示具体问题
        通过 → 保存活动，出现在活动大厅
→ 我的活动：查看每个活动报名人数
   → 查看报名名单（姓名/学号/手机号/报名时间）
   → 关闭报名（学生端即不可报名）/ 误操作时重新开放
```

## 4. 数据设计

数据保存在 localStorage，共三类业务对象 + 会话：

### 4.1 用户 User（键：cas_users，数组）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | string | 用户唯一标识 |
| username | string | 登录名，注册时校验唯一 |
| passwordHash | string | 密码哈希值（SHA-256，非明文） |
| name | string | 姓名/昵称 |
| role | string | 角色：student / teacher |
| createdAt | string | 注册时间 ISO 字符串 |

### 4.2 活动 Activity（键：cas_activities，数组）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | string | 活动唯一标识 |
| title | string | 活动标题（必填） |
| description | string | 活动描述 |
| location | string | 活动地点（必填） |
| startTime | string | 活动开始时间（必填） |
| endTime | string | 活动结束时间（必填，晚于开始时间） |
| capacity | number | 名额上限（正整数） |
| deadline | string | 报名截止时间（不晚于开始时间） |
| publisherId | string | 发布教师 id（关联 User.id） |
| publisherName | string | 发布教师姓名（冗余，便于展示） |
| status | string | open / closed（教师手动关闭） |
| createdAt | string | 发布时间 |

### 4.3 报名记录 Registration（键：cas_registrations，数组）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | string | 报名记录唯一标识 |
| activityId | string | 活动 id（关联 Activity.id） |
| studentId | string | 报名学生 id（关联 User.id） |
| studentName | string | 学生姓名（冗余） |
| studentNo | string | 学号（报名时填写，必填） |
| phone | string | 手机号（报名时填写，必填，11 位数字） |
| status | string | registered / cancelled |
| createdAt | string | 报名时间 |

### 4.4 会话 Session（键：cas_session）

保存当前登录用户 id；页面加载时恢复登录状态；退出登录时清除。

### 4.5 实体关系

- 一个教师可以发布多个活动（1 : n，User(teacher) → Activity）。
- 一个学生可以创建多条报名记录（1 : n，User(student) → Registration）。
- 一个活动可以有多条报名记录（1 : n，Activity → Registration）。
- 报名记录是学生与活动之间的关联类，承载学号、手机号、报名时间、状态。
- 名额判断：某活动 status=registered 的记录数 < capacity。

## 5. 关键设计决策

1. **身份与权限**：注册时确定角色；前端导航按角色渲染，且所有写操作（发布、报名、关闭、取消）在业务逻辑层再次校验角色与数据归属，不依赖"按钮隐藏"作为唯一防线。
2. **活动状态判定**：不新增"已结束"等冗余状态。是否可报名由 `status == open` 且 `当前时间 <= deadline` 共同决定，避免状态与时间不一致（如教师忘记关闭）。
3. **重复报名规则**：以"该学生对该活动是否存在 status=registered 的记录"为准；取消报名后记录保留为 cancelled（可追溯），学生可重新报名。
4. **名额控制**：报名与取消在同一数据读写流程内完成并立即写回 localStorage，保证人数与名单始终一致。
5. **表单校验集中化**：活动发布与报名各有一个校验函数，返回第一条错误信息直接提示，保证"异常流程"可验收。
6. **安全基线**：密码经 SHA-256 哈希后存储（不可用环境下退化为内置哈希，亦非明文）；所有用户输入渲染到 HTML 前统一转义，防止注入。
7. **技术选型与可演化性**：数据访问层与视图层分离，V1.0 用 localStorage，后续接入服务端时只需替换 storage.js 的实现。
