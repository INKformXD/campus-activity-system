# 校园活动管理系统 V3.0 需求与设计说明

> 本文档记录实验三（基于运行数据的需求演化）中，V2.0 → V3.0 的需求判断、设计与实施边界。
> 数据依据见 `lab3-analysis/`（分析脚本、指标与图表），数据本身为教师提供的模拟运行数据，不代表本组系统真实日志。

## 1. 分析口径

| 项目 | 说明 |
| --- | --- |
| 分析对象 | `registration_log.csv`（2878 条业务请求）、`waitlist_log.csv`（1006 条状态变化）、`activity.csv`（24 个活动）、`feedback.csv`（112 条匿名反馈）、`user_behavior.csv`（11027 条埋点）、`system_log.csv`（792 条日志） |
| 时间范围 | 2026-09-21 至 2026-10-04（个别状态查询记录延至 10-07） |
| 观察单位 | 报名申请以 `registration_log` 中 `action=apply` 的请求计（n=2748）；候补以 `application_id` 唯一计数（n=876） |
| 限制 | 模拟数据，只能证明"现象存在"，不能证明原因；分表粒度不同，访问次数、申请次数、人数不混用；反馈为非结构化文本，按关键词归类的条数不等于用户比例 |

## 2. 数据发现（观察事实）

1. **候补是常态而不是例外**：2748 条报名申请中，876 条（31.9%）进入候补，1689 条（61.5%）直接确认。876 个候补申请中只有 130 个（14.8%）最终转正，转正等待时长中位数 18.1 小时，P90 为 46.3 小时。
2. **报名结果的不确定性有明确行为痕迹**：126 条重复提交且 `client_retry` 全部为 1；16 条 `server_error`；反馈中 19 条（17.0%）直接描述"不确定是否提交成功/连续点了两次/页面卡住又点一次"。
3. **候补与状态变化缺少可见入口**：112 条反馈里 33 条（29.5%）指向候补或状态变化难追踪（"经常自己去查状态""隔了两天打开页面才发现""登录后才知道"）；埋点中"报名状态页"被访问 293 次，接近报名页（252 次），说明学生在反复自查。
4. **热门活动申请量远超名额**：24 个活动中 17 个已满员，其余也达到 79% 以上，申请量中位数 94.5、名额中位数 75.5；前 5 个活动申请数约 200、名额 31~43，候补率 66%~73%。
5. **峰值集中在报名开放时刻**：09:00 与 18:00 两个时点共占请求 45%，09:00 单点占 29.1%；满员/名额冲突请求的耗时中位数 1308 ms，是直接确认（215 ms）的 6 倍，服务端另有 250 条 `SLOW_REQUEST` 告警。
6. **反馈中仍有 22 条（19.6%）指向"活动难找"**，但活动仅 24 个、且本组 V2.0 活动数据没有类型字段；10 条（8.9%）指向地点、时间等细节。

## 3. 需求判断

V2.0 已实现候补 FIFO、条件审核与自动补位，但**状态变化发生在后台，学生没有可靠的方式知道自己"现在是什么状态、刚刚发生了什么"**。数据同时显示：候补占比高、转正等待长、重复提交多、状态页被反复查看、反馈主题第一。

因此本轮选择**深入解决一个问题**："报名与候补过程的状态可见性"，而不是新增活动发现类功能。

| 编号 | 需求 | 依据 | 验收要点 |
| --- | --- | --- | --- |
| REQ-10 | 站内消息中心：报名结果、审核结果、候补转正发生时，系统为学生生成一条可回看的状态消息，并在导航栏显示未读数 | 发现 3、1；反馈 33 条 | 消息持久化；刷新后仍在；打开后未读清零；消息含活动名、状态与时间 |
| REQ-11 | 候补队列透明化：我的报名显示"候补第 N 位/共 M 人"，状态变化后卡片标记"有新变化"，并展示最近变化时间 | 发现 1、3 | 位置随队列变化更新；转正后不再显示候补；新变化标记随消息已读消除 |
| REQ-12 | 报名提交幂等与明确回执：提交按钮进入"提交中"并禁止重复提交；同一学生对同一活动重复提交返回同一条记录与同一回执号，而不是再产生一条申请 | 发现 2；反馈 19 条 | 连续提交两次只产生 1 条报名；回执号一致；结果面板关闭后仍可在我的报名中看到回执 |

**取舍说明**：
- "活动筛选/搜索"（反馈 22 条）证据同样存在，但需要给活动补类型字段、改发布表单与列表交互，与"状态可见性"不是同一问题域；本轮 2 学时，先保证一条主线做透，故列入下一轮候选。
- "站外推送/短信提醒"不可行（纯前端原型、无服务端通道），V2.0 已明确该边界；本轮用"下次进入系统即可看到"的站内消息替代，不承诺实时性。
- "候补响应时限/超时释放"缺少业务规则依据（教师访谈未确认），不实现。

## 4. 设计

### 4.1 数据层（`js/storage.js`）
新增通知集合 `cas_notifications`：

```
{ id, userId, activityId, type, title, message, createdAt, read }
type ∈ { confirmed, waitlisted, pending, promoted, rejected }
```

- `getNotifications(userId)` / `addNotification(n)` / `markNotificationsRead(userId)` / `unreadCount(userId)`
- 注销账户时同步清理该用户的通知（延续 REQ-09 的级联删除约定）
- 报名记录新增 `requestNo`（回执号）与 `lastChangeAt`（最近状态变化时间），不改变既有字段语义

### 4.2 业务层（`js/app.js`）
1. **提交过程**：点击提交 → 按钮 `disabled` 且文案为"提交中…" → 400 ms 后写入并返回回执 → 弹窗内切换为结果面板（状态说明 + 回执号 + 两个入口）。`submitting` 标志在写入完成前拦截重复提交。
2. **幂等**：写入前先查该学生对该活动的有效报名（registered/pending/waitlisted），存在则直接返回既有记录，回执号不变，不新增记录。
3. **通知触发点**：报名写入、教师审核（通过→确认/候补、不通过）、已确认者取消导致的队首补位。
4. **未读与已读**：导航"消息"按钮显示未读数；打开消息中心即全部标记已读；我的报名卡片对"有未读消息的活动"显示"有新变化"。
5. **候补位置**：沿用 V2.0 的 `createdAt` FIFO 顺序，展示"第 N 位 / 共 M 人"。

### 4.3 界面层
- 导航新增"消息"入口（仅学生）
- 消息中心为弹窗列表，按时间倒序，未读加粗
- 报名结果面板替代原来"2.6 秒后消失的 toast"作为正式回执

## 5. 实施边界
- 仅更新浏览器 localStorage，不提供跨设备/跨浏览器的实时推送。
- 不改变 V1.0/V2.0 已有业务规则：名额只由已确认占用、候补 FIFO、条件审核、截止/关闭校验、权限与级联删除均保持。
- 移动端适配（数据中移动端占 71%）本轮不处理，原因是改动集中在 CSS 布局、与状态可见性主线无关，列入下一轮候选。
